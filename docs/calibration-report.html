Part A — Playbook

What works, what fails, exact commands, measured numbers. Supersedes where it conflicts with Part B.

If you read one thing: The ultra-wide Max-Lens-Mod fisheye is calibratable from ordinary USB-webcam frames: Double Sphere via OpenImuCameraCalibrator (OpenICC) gives 0.6–1.1 px, and is now integrated into the calibrator (§12). Two traps cost us days: a marketed-as-clean mode that is anamorphic (177° Max HyperView, §3), and a caib.io board-layout parity bug (§11) that silently corrupted every solve on even-column boards and masqueraded as "the lens is impossible". With the layout fixed, even cv2 pinhole/fisheye solve the webcam circle at ~1.2–1.3 px (center-weighted); Double Sphere remains the correct full-view model. Jump to §6 recipe, §10 commands.

1. Purpose & how to use this

This is a reproduction-grade record of how to calibrate an ultra-wide GoPro (Max Lens Mod) fisheye for a UMI-style robotics pipeline, written so an agent can act without re-deriving anything. It states, with measured numbers, what works, what fails, the exact stacks/commands, and the gotchas. Confidence tags: verified (measured/confirmed against a primary artifact), inferred (consistent, not directly demonstrated), corrected (a claim we revised mid-investigation).

5. Capture interfaces — and the webcam correction

Correction (this supersedes earlier docs). Earlier reports said USB-webcam mode "can't use the Max Lens Mod" and is a dead end. That was wrong. It was a cv2-solver limitation, not a webcam one. Measured: the webcam-Wide frames (with the mod) are the same circular fisheye as the recording, and a Double Sphere solve on them gave 0.617 px — actually better than the recording (0.82 px), with healthier params (alpha 0.708 vs pinned 1.0). corrected

6. The winning recipe (exact)

  1. Build OpenICC (Docker; self-contained — Ubuntu 22.04 + apt OpenCV-contrib + Ceres 2.1 + pyTheiaSfM). ~10 min: 
    # clone (or use the repo's own Dockerfile)
git clone --depth 1 https://github.com/urbste/OpenImuCameraCalibrator /tmp/openicc
  2. Adapt the board to ours — one line in /tmp/openicc/applications/extract_board_to_json.cc (OpenICC hardcodes marker = square/2; ours is 15/21): 
    const float aruco_marker_length = FLAGS_checker_square_length_m * (15.0f / 21.0f);  // was /2.0f
    The dictionary stays a runtime flag (--aruco_dict=0 = DICT_4X4_50). Then: 
    cd /tmp/openicc && docker build -t openicc .
  3. Feed frames. OpenICC takes a video file (cv::VideoCapture) or a directory globbing *.png whose filenames are nanosecond timestamps. For pre-extracted JPGs, hardlink them to <ns>.png (cv::imread decodes by content, so no re-encode): 
    for f in frames/capture_*.jpg; do n=${f//[^0-9]/}; ln "$f" "wcframes_png/$((10#$n*33333333)).png"; done
    (Or assemble an mp4: ffmpeg -framerate 30 -i capture_%03d.jpg -c:v libx264 -pix_fmt yuv420p wc.mp4.)
  4. Extract corners + calibrate Double Sphere (foreground, bounded — see §10 for the full command): 
    extract_board_to_json --input_path=<dir-or-mp4> --board_type=charuco --aruco_dict=0 \
   --num_squares_x=10 --num_squares_y=7 --checker_square_length_m=0.021 \
   --save_corners_json_path=corners.uson
calibrate_camera --input_corners=corners.uson --camera_model_to_calibrate=DOUBLE_SPHERE \
   --grid_size=0.1 --save_path_calib_dataset=out
    Result is out.json (intrinsic_type DOUBLE_SPHERE: focal, principal_pt, xi, alpha, aspect, final_reproj_error).

7. Capture-quality guidance

  • Sweep the whole circle. Push the board into every region incl. the curved edges/corners, near & far, lots of tilt. Under-coverage shows up as alpha → 1.0 (boundary) — seen on the recording (0.82 px, alpha 1.0) vs the better-distributed webcam set (0.617 px, alpha 0.71).
  • Bigger board / closer so markers are large and crisp; 20–40+ good views; fast shutter; good light.
  • Stabilization (HyperSmooth) OFF, horizon lock OFF — they warp frames non-rigidly.
  • Never anamorphic modes (SuperView/HyperView/Max HyperView). Use the clean fisheye (webcam Wide, or Max SuperView when recording).

8. UMI alignment

UMI uses a GoPro HERO 9 + 155° Max Lens Mod 1.0, calibrates a Kannala–Brandt fisheye with OpenICC (the same tool here), feeds raw fisheye to the policy, and recovers gripper pose with an ORB-SLAM3 fork + GoPro GPMF IMU from recorded mp4; live deploy is via HDMI capture. Matching 155° exactly is not required — UMI is lens-agnostic given recalibration (drop the intrinsics into its .json + ORB-SLAM3 .yaml). Our Double Sphere output is OpenICC's native format. verified (UMI paper/repo, issue #41)

9. Caveats, confidence & corrections

  • caib.io layout parity varies by board dimensions — the earlier "board verified correct" claim was wrong in detail (geometry right, marker parity mirrored); now auto-detected per solve (§11). The catastrophic cv2 numbers on this board were layout-corrupted. corrected
  • OpenICC view filter is absolute (~2 px) → 4K solves must run at ≤1080p coordinate scale (the in-app integration auto-downscales and rescales intrinsics). verified
  • Webcam mode IS calibratable for the MLM (0.6–1.1 px). The old "webcam dead end" was a cv2 limitation. corrected
  • "177°" is Max HyperView = anamorphic, uncalibratable; the clean wide fisheye is Max SuperView 167°. corrected
  • No OpenCV model calibrates ≥~150° here: pinhole geometric-limited; cv2.fisheye hits its ~180° wall; cv2.omnidir's 4.13 binding is broken/divergent. verified
  • cv2.fisheye works ≤~130–140° (1.12 px) — fine for native Wide if you drop the mod. verified
  • Our DICT_4X4 board works in OpenICC after the one-line marker edit + --aruco_dict=0; corners detected on all frames (no re-print needed). verified
  • Kalibr/Basalt need AprilGrid, not ChArUco. verified
  • UMI uses Kannala–Brandt (committed intrinsics file), not Double Sphere — though OpenICC offers both; DS worked best for us at 167°. verified
  • alpha→1.0 = weak coverage, not a failure; tighten with a full-field sweep. verified
  • GoPro `fov=` over webcam is unreliable (OpenGoPro #459, WONTFIX) — verify the streamed FOV by eye. inferred
  • Run-folder names are unreliable (default camera_name gopro13_hyperview mislabels non-HERO13 data). verified
  • Operational: long solves/builds must be run foreground with a bounded timeout, judged by on-disk artifacts — background "fire-and-forget" pings are unreliable. corrected

11. The caib.io board-layout parity bug (major correction)

This invalidates the earlier "board verified correct" claim. caib.io boards place markers on alternating checkerboard cells, but which parity row 0 starts on varies with the board's dimensions (corner colour). Our 11×8 DICT_5X5 board matched the assumed parity (so it calibrated at 1.12 px and "validated" the builder); the 10×7 DICT_4X4 board is mirrored — every odd-row marker sat one full square away from where the model said. Symptom: a ~52–108 px "uncalibratable" solve that looks exactly like a hopeless lens, while the per-view median residual stays small (even rows fit) and entire odd marker rows are outliers.
  • How it was found: homography cross-check per marker id — ids 5–9, 15–19, 25–29 (= odd rows) all off by ~75 px ≈ one square; testing the four parity layouts gave 1.9 px for (row0→odd cols) vs 37 px for the assumed one.
  • Fix in the calibrator: detect_board_layout() — both parities are scored against the actual detections with a RANSAC homography (median per-corner residual over the 5 best views) and the better one wins; the choice is recorded as board.layout: standard|flipped in the run summary. Zero configuration.
  • Lesson for agents: when a planar-board calibration is bad at the "tens of px" scale but the median residual of a homography fit is a few px, suspect a layout/id-mapping mismatch, not the lens. Check residuals per marker id — structured outliers (whole rows/columns) = wrong board model.
  • Knock-on effect: with the layout fixed, even cv2 pinhole/fisheye produce ~1.2–1.3 px on the webcam circular fisheye (over auto-selected, center-weighted views). The model hierarchy still holds — cv2.fisheye keeps failing on the 4K recording with edge coverage, and Double Sphere is the only model valid across the whole image — but the catastrophic numbers earlier were the layout bug, not pure lens physics.

12. In-app Double Sphere (OpenICC integration)

The calibrator now solves double_sphere natively by driving OpenICC as an external backend:

  • Mechanism: the app's own ArUco detections are written as OpenICC's UBJSON corners file (scene_pts id = marker_id*4 + corner_index, views keyed by synthetic µs timestamps — verified: calibrate_camera treats them as arbitrary 3D↔2D correspondences, no board structure assumed). Then calibrate_camera --camera_model_to_calibrate=DOUBLE_SPHERE runs in Docker (--user uid:gid, bounded timeout, unique container name killed on timeout), and the result JSON is mapped into the standard result shape. No OpenICC extractor, no board reprint, no marker-length hack.
  • License (AGPL-3.0): strict subprocess + file exchange; nothing imported, linked, or vendored. The operator builds the openicc image themselves (repo Dockerfile, ~10 min).
  • Config (env vars): OPENICC_DOCKER_IMAGE (default openicc), OPENICC_BINARY (native build escape hatch), OPENICC_GRID_SIZE (0.1), OPENICC_TIMEOUT_S (360), OPENICC_DOCKER_ROOT.
  • Selection: UI "Calibration model" → Fisheye + Double Sphere or Double Sphere only; the UMI gripper preset ships models: [fisheye, double_sphere] (fisheye = docker-less fallback).
  • Artifacts: <camera>_double_sphere.json (UMI/OpenICC-native: focal, principal point, aspect, xi, alpha, error) at native resolution, plus openicc/calibrate_camera.log for diagnostics. No ROS YAML for this model (camera_info has no double-sphere standard — deliberate).
  • 4K gotcha (handled): OpenICC drops views above an absolute ~2 px threshold, which unfairly kills 4K solves (2 px at 4K = 1 px at 1080p). The integration auto-downscales coordinates to ≤1080p for the solve and scales focal/principal/error back to native (solve_downsample_factor recorded in the artifact).
  • Failure semantics: any backend failure (no docker, missing image, timeout, non-convergence, <10 usable views) surfaces as a failed-model row (ok: false + message) — other models still solve.

14. Multi-camera sync for dataset recording

For UMI-style recorded datasets (multiple GoPros, mp4 + GPMF):

  • Primary: audio clap cross-correlation — one sharp clap on set; cross-correlate the 48 kHz audio tracks (FFT) → sub-ms relative offsets, no special firmware needed. This is the precision layer; everything else is optional. (The "FFT a clap" instinct — it's the standard trick.)
  • Optional: GoPro Labs "Time/date/timecode QR Code" for absolute wall-clock anchoring (pairing footage with robot/host logs). Nuance on the simultaneity worry: the QR encodes absolute UTC, so cameras do not need to scan it at the same moment — each sets its clock at its own scan. The residual is each camera's scan-to-set latency (ms-level, unverified) — which is exactly why the clap stays primary. The same anchoring works without Labs by filming an on-screen millisecond clock with each camera.
  • Labs verdict for everything else (verified against the Labs extensions page): Labs exposes nothing for the USB webcam/UVC path — no webcam FOV/resolution/lens command exists, so Labs cannot "fix" the unreliable webcam fov=; verify the streamed FOV visually instead and don't pursue Labs for webcam behavior. EXPQ (fixed shutter) and WBLK (white-balance lock) exist but are capture-scoped (webcam effect unverified). Treat Labs as optional, recording-mode tooling.
  • Alternative absolute sync: Labs GPS time sync (outdoor).
  • Live-streamed cameras (USB webcam → one host): frames are timestamped on arrival by the host clock — one clock, no cross-camera offset, jitter ≈ a frame period. Nothing extra needed at deploy time.
  • Orchestration: BLE record start/stop to all cameras gets captures roughly together (not frame-accurate — that's what the QR + clap are for).
  • Also from Labs, useful here: Max Shutter Angle (fast fixed shutter → crisp ChArUco corners), White Balance Lock, Wake on Power (camera comes up with the robot), HDMI display settings (clean HDMI for capture-card deployments).
  • Rehearsal to run once on real hardware: two cameras film the time-QR, then a clap, record 2–3 min; cross-correlate audio → measured offset + drift. That number validates the whole recipe.

15. Board choice, dictionary interference & the printable A3 board

Recommendation flip: the primary calibration board should be the existing 11×8 DICT_5X5_100 calib.io board (34 mm squares / 25 mm markers, A3) — bigger squares, a modern small dictionary, already printed, and zero interference with the DICT_4X4 markers on the grippers.
  • OpenICC's board spec is a tool default, not a best practice. DICT_ARUCO_ORIGINAL is the legacy 1024-marker dictionary with weak inter-marker Hamming distance (more mis-identifications); modern practice prefers a small purpose dictionary (DICT_5X5_50/100 class) for maximum robustness. The marker = ½·square ratio is merely hardcoded in their extractor for convenience — calib.io's fatter markers (≈0.71 ratio) carry more pixels per marker and detect better. Since the in-app integration (§12) writes correspondences from our own detector, neither constraint applies to our pipeline; they matter only when running OpenICC's own extractor (e.g. the future IMU-calibration pipeline). assessed (established ArUco practice; not re-benchmarked here)
  • Dictionary interference with the gripper markers (DICT_4X4) is real. If the calibration board shares the gripper dictionary and id range, any gripper/scene marker in frame injects false 3D↔2D correspondences — the same outlier class as the layout bug, and it can also confuse gripper-marker tracking when the board is visible at runtime. Rule: calibration boards and functional (gripper) markers must use different dictionary families. 5X5 board + 4X4 grippers = no cross-decoding (different bit-grid sizes).
  • Printable A3 board (optional), generated to OpenICC's stock spec: docs/openicc_charuco_A3_10x7_40mm_dictoriginal.png + print wrapper docs/print_openicc_board_a3.html — 10×7 squares, 40 mm square / 20 mm marker (=½·square, so OpenICC's unmodified extractor accepts it), DICT_ARUCO_ORIGINAL ids 0–34, 300 DPI A3 canvas with pHYs so "print 100%" is physically exact (verify a square = 40.0 mm). It is also 4×4-safe. Use it for OpenICC-extractor parity work; otherwise prefer the 5X5 board above.
  • Caveat on our Docker image: the openicc image we built carries the one-line marker-ratio edit (15/21) binding their extractor to the 21 mm DICT_4X4 board. That edit is irrelevant for the in-app path (own corners) and for this new ½-ratio board a stock clone works; rebuild from a clean clone (or make the ratio a flag) if mixing boards through their extractor.

16. 4K, downscaling & which model — direct answers

  • "Is the 4K downscale a problematic blackbox transform?" — No. The corners are still detected at full 4K sub-pixel precision; the integration only changes units: pixel coordinates ÷2 into the solver, focal/principal ×2 back out (an exact linear rescale; xi/alpha are scale-free). No image is resampled and no precision is lost. The only real effect is that OpenICC's absolute ~2 px view-rejection threshold then operates at a sane scale — which is precisely the point (2 px at 4K ≡ 1 px at 1080p; without the rescale, equally good 4K solves get their views purged and the run dies). solve_downsample_factor is recorded in the artifact for full transparency.
  • "Should we do everything at 1080p?" — No; match the deploy mode. Calibrate in the exact mode each camera is used: 1080p webcam for the live robot feed (that's what the app captures), 4K recording for recorded datasets/SLAM. Forcing everything to 1080p would throw away recording-mode resolution for no accuracy gain — the rescale already neutralizes the threshold issue.
  • "Fisheye now solves — use it instead so we can calibrate at 4K?" — No (slight overthink). Three reasons: (1) cv2.fisheye still fails the 4K recording (edge coverage past the KB wall) — it only solved the webcam set; (2) its 1.19 px is computed over auto-selected, center-weighted views — Kannala–Brandt misfits the extreme periphery, which is exactly where the UMI side-mirrors live, so a KB calibration is least trustworthy precisely where the gripper pipeline needs it most; (3) 4K is no obstacle for Double Sphere (the rescale is a unit change). Keep [fisheye, double_sphere] — DS primary, KB as the docker-less fallback and cross-check.

1. Basics (plain language)

Calibration
Measuring a lens's "character" — how it bends the image and where its optical center is — so we can recover real geometry (distances, angles, motion) from pictures.
Intrinsics
The numbers describing that character (focal length, image center, distortion coefficients). The output of calibration.
Distortion
Bending of straight lines. Wide lenses bend hard (the "fisheye" look).
Field of view (FOV)
How much of the world the camera sees, in degrees. Bigger = wider.
Fisheye
A wide lens that curves the edges; needs a special math model.
Anamorphic
A directional stretch that squeezes one part of the image more than another (not a clean radial bend) — so no lens model fits it. GoPro SuperView/HyperView do this.
Pinhole / rectilinear
A narrow lens where straight lines stay straight. Easiest to calibrate, but narrow FOV.
Reprojection error
How accurate a calibration is, in pixels. Under ~1px is great; 30–50px means unusable.
ChArUco board
A checkerboard with markers, filmed from many angles to measure the lens.
SLAM
An algorithm that recovers a camera's 3D path from video (optionally + motion sensors).
UMI
"Universal Manipulation Interface" — a robotics project that uses a GoPro to collect demonstrations. We're building something similar.

2. The key idea: physical lens vs digital mode

Everything downstream depends on this. There are two layers:

  • The physical lens — real glass in front of the sensor; decides how much of the world enters. A stock GoPro sees ~120–130°. The Max Lens Mod is extra glass that widens the view — the clean fisheye it adds is 155° (v1.0) or 167° (v2.0, "Max SuperView"). (The 2.0's headline "177°" is a separate anamorphic mode — see §4.)
  • The digital mode (Wide / Linear / SuperView…) — software cropping/"straightening" of what the lens already captured.

So "Linear" is not a narrow lens and "Wide" is not a Max Lens Mod. The mod physically captures more of the world than any digital mode can invent.

More detail
Digital lenses are reprojections/crops of one sensor image. "Linear" is a rectilinear projection (straight lines stay straight) and is inherently narrow — at ~155° a rectilinear image stretches the edges toward infinity, so Linear yields ~90–110° regardless of the glass in front of it. Critically, the camera only outputs a processed crop, never the raw sensor — so the camera can "discard" the wide periphery by cropping it before output. That is exactly what makes the same physical lens look different over webcam vs recording vs HDMI.

SuperView / HyperView must never be used for calibration or deployment. They stretch the 4:3 / 8:7 sensor to 16:9 non-uniformly (center less, edges more) — not a radially-symmetric projection, so no pinhole or fisheye model fits it. verified (Don't confuse names: the lens-mod's "Max SuperView" in §4 is a different, clean fisheye mode from the digital "SuperView" here.)

More detail · sources
Joshi et al. (GoPro underwater VI-SLAM, ICRA 2022) state verbatim that SuperView "generates non-linear distortions that thwart the calibration of the camera's intrinsic parameters," and used Wide at 1960×1080/60, HyperSmooth off, H-FOV 118° / V-FOV 69°. Gyroflow's docs likewise call SuperView/HyperView a "proprietary stretching equation which is not exactly mapped" and recommend Wide. GoPro 16:9 Wide is ~122–123° diagonal on HERO12/13. Note: GoPro "Linear" itself is a firmware de-fish with an EIS crop, so treat it as pinhole only with stabilization off.

The 177° trap. The "177°" GoPro markets for the 2.0 is Max HyperView — a non-uniform anamorphic stretch (an 8:7 frame dynamically squished into 16:9), the same family as ordinary SuperView/HyperView. It is not a clean fisheye, and no standard model (fisheye, Double Sphere, omnidir) can calibrate it. The widest clean, radially-symmetric fisheye on the 2.0 is Max SuperView = 167° — that is the mode to use. verified (GoPro engineer A. Kislevitz)

Can a GoPro 13 hit UMI's 155°? No — and it doesn't matter

  • There is no clean ~150–160° lens on a HERO 13. Your clean-fisheye choices are native Wide ~123° (a touch narrow) or MLM 2.0 Max SuperView ~167° (a touch wide). Exactly 155° belongs to the original Max Lens Mod 1.0, which GoPro does not list for the HERO 13 (HERO 9–12 only; the "HERO13" seen in some shop listings is a retailer artifact, and there are poor-physical-fit reports). verified
  • Matching 155° is not required. UMI feeds raw fisheye to the policy and is lens-agnostic given recalibration — you recalibrate whatever clean wide fisheye you use and drop the intrinsics into the UMI .json (and the ORB-SLAM3 .yaml). What matters is a clean wide fisheye plus identical capture settings at training and deployment, not the exact degree. verified (UMI issue #41)

Bottom line for the 13: use Max SuperView (167°) for the wide, UMI-style cameras, or native Wide (~123°) where less FOV is acceptable — never Max HyperView (177°). And note these clean "Max" modes exist only when recording or over HDMI, not in USB webcam mode (§8). verified

5. Which math model works for which field of view

The wider the lens, the more capable the model must be. Where each of our lenses lands:

pinhole fisheye / Kannala–Brandt Double Sphere uncalibratable

The models, in plain terms

  • Pinhole (plumb_bob / rational) — the basic model. Works to ~90–95°. The 8-coefficient "rational" variant stretches that slightly but does not rescue ~130° Wide.
  • Fisheye (Kannala–Brandt) — the standard fisheye model; good to ~140–150°. In OpenCV it has a hard wall near 180° and degrades well before that.
  • Double Sphere / EUCM (Enhanced Unified Camera Model) / omnidirectional — the specialist models for ~150–195°. These are what you need for a clean wide Max-Lens-Mod fisheye (e.g. Max SuperView 167°). OpenCV does not provide Double Sphere built-in (Kalibr and OpenImuCameraCalibrator do).
More detail · thresholds & gotchas
MathWorks Computer Vision Toolbox: pinhole modeled up to 95°, Kannala–Brandt to 115°, Scaramuzza (omnidir) to 195°, and "the pinhole model cannot model a fisheye camera." Tangram MetriCal: RadTan best ≤90°, OpenCV-Fisheye ≤140°, Pinhole+KB ≤140°, Omnidirectional >140°. Double Sphere paper (arXiv 1807.08957): "pinhole … suboptimal for FOV > 120°"; test lenses 122–195° incl. a 150° GoPro lens; DS within <1% of KB-8 accuracy and faster, with a closed-form inverse and no z=0 singularity.

cv2.fisheye is fragile. Use CALIB_RECOMPUTE_EXTRINSIC | CALIB_FIX_SKEW | CALIB_CHECK_COND; object points must be shaped (N,1,3); when CALIB_CHECK_COND throws ("Ill-conditioned matrix for input array N") the cure is to drop that frame, not disable the check; a related failure is InitExtrinsics: fabs(norm_u1) > 0 on degenerate views. Model vs implementation: the KB model can exceed 180°; it's OpenCV's/Kalibr's pinhole-then-distortion implementation that hits the 180° wall (the TUM Double Sphere page notes KB can fit a 190° lens with a proper implementation). ROS caveat: ROS image_proc pinhole rectification does not correctly consume equidistant fisheye intrinsics (image_pipeline #682) — use a fisheye-aware undistort (cv2.fisheye.initUndistortRectifyMap / estimateNewCameraMatrixForUndistortRectify) and accept FOV cropping when producing a pinhole output.

6. What UMI actually does (the reference pipeline)

UMI is the closest real precedent, so its choices are the benchmark:

  • Camera: a wrist-mounted GoPro HERO 9 with the original 155° Max Lens Mod (1.0) — a physical lens, plus GoPro Labs firmware. verified
  • Intrinsics model: the committed UMI calibration file is Kannala–Brandt fisheye (intrinsic_type: FISHEYE, 4 coefficients, 0.29px reprojection), calibrated with Steffen Urban's OpenImuCameraCalibrator (which also offers Double Sphere / EUCM / Division-Undistortion). verified
  • Action labels (pose): an ORB-SLAM3 fork (inertial-monocular) recovers the gripper's 3D trajectory from the fisheye video + the GoPro's built-in IMU (accel/gyro embedded in the mp4 as "GPMF"). That trajectory is the demonstration's action label. verified
  • The policy uses raw fisheye images (no rectification) — rectifying a 155° lens to pinhole produces extreme edge distortion, unsuitable for learning. Physical side mirrors add implicit stereo. verified
  • Data collection = recorded mp4 (processed offline). Deployment = live, via HDMI capture (see §10). The handheld demo device has no live link. verified
  • FastUMI (a follow-up) kept the GoPro fisheye image but replaced GoPro/ORB-SLAM3 pose tracking with a RealSense T265, citing the GoPro VIO (visual-inertial odometry) pipeline as fragile and calibration-heavy. Its GoPro image still goes through an HDMI capture card. inferred (HDMI path inferred from its Elgato HD60 X use)
Takeaway: UMI never calibrates with a simple webcam tool, and never uses USB webcam mode. It records, calibrates offline with a fisheye/Double-Sphere-class tool, and streams live over HDMI. Our situation only differs in the camera body (HERO 13 + MLM 2.0 → a 167° clean fisheye, "Max SuperView", instead of 155°), which pushes us from "Kannala–Brandt is marginal" into "Double Sphere is the safe choice."

7. What we observed in our own tests

7.1 A wide lens looked like a fisheye; a narrow one looked flat — huge error

A pinhole calibration handles a narrow/near-flat capture nicely (~1–2px). The moment the lens is genuinely wide, pinhole cannot represent it and the error explodes. Model limitation, not a setup mistake.

7.2 A capture at ~30px (SuperView, 720p)

One real run was shot in SuperView at 720p (these were the default settings at the time). Reprojection ~27–44px — exactly what an uncalibratable anamorphic mode produces.

7.3 "Results: n/a" on the Max-Lens-Mod capture

The MLM 2.0 camera over USB webcam (Wide, 1080p), calibrated with a fisheye model: 108 frames captured, no result written → "n/a". Over webcam the camera doesn't apply lens-mod processing, so the image was the unprocessed wide circular fisheye with black corners; the fisheye solve broke on it (this near-180° regime is beyond the basic fisheye model) and saved nothing — and the UI failed to surface the error, so it looked like a silent failure.

We verified the board was not at fault. A sweep of plausible board geometries showed cols=10, rows=7 fits at 52px while every other geometry gives 200–1000px; the highest detected marker ID was exactly 34 (= 35 markers). So the board config was correct — the failure is the unprocessed wide lens over webcam, not the board and not a bug. A bigger board (like the GoPro 11 one that gave sub-pixel results) improves precision and is recommended, but does not fix the lens/mode problem.
More detail · reproduced on the real frames
Run gopro13_umi_gripper_20260610_140106: 108 frames, no summary → fisheye raised "could not converge". On these exact frames: pinhole 52px; cv2.fisheye fails to converge; cv2.omnidir 48px and/or diverges, keeping only ~10 of 103 frames (numerically unstable — even with CALIB_FIX_SKEW it blew up). So no OpenCV model calibrated this unprocessed wide circular image. For contrast, cv2.fisheye on a narrow Wide capture measured 1.12px — the model is fine in range; a near-180° image is out of range. (Also note: many run folders were auto-named gopro13_hyperview_* from a default name and are mislabeled — they are not GoPro 13 data; treat run-folder names with suspicion.)

8. Why USB webcam mode can't use the Max Lens Mod (the black corners)

With the mod attached, the lens throws a wide circular image onto the sensor. In USB webcam mode the camera does not apply Max-Lens-Mod processing — it can't be told the mod is there and uses the stock Wide geometry. So the circular image doesn't fill the frame → black corners (vignetting). Not fixable in webcam mode. You get the worst of both worlds: extreme wide distortion (hard to calibrate) without a clean image.

When the GoPro records or outputs over HDMI, it does run the lens-mod processing, so those images are clean. That single fact splits the three options below.

More detail
The Open GoPro webcam FOV set is only WIDE/NARROW/SUPERVIEW/LINEAR, ≤1080p, and the fov= request is unreliable (Open GoPro issue #459, WONTFIX) — on several firmwares the camera streams whatever lens it's set to, so verify the streamed FOV empirically rather than trusting the dropdown. This matches what we saw earlier (HERO11 "Wide" and "SuperView" both looked flat over webcam).

9. The simplest way to get a calibration right now: offline, by hand

If the only immediate goal is the camera's intrinsics, no capture card is needed:

  1. Record a short clip (or stills) of the ChArUco board through the real lens — move it to cover the whole frame and many tilts. Because this is recording, the camera applies the Max-Lens-Mod processing, so the image is clean (no webcam vignette).
  2. Copy the file off the SD card and extract frames on the computer.
  3. Calibrate offline with a model matching the FOV — Double Sphere for Max SuperView (167°); the basic fisheye only up to ~130–150° (e.g. native Wide ~123°). Set the lens to Max SuperView, never Max HyperView.

This is exactly how UMI obtains its calibration, and it also covers the recorded human-demonstration data (offline anyway).

The catch — streaming for the robot. Offline frames cannot drive a robot. The moment a live feed is needed (the policy running in real time), USB webcam can't do the Max Lens Mod, so the live path must be HDMI → capture card. Plan: offline now to unblock calibration; HDMI for live deployment.

10. The live deployment path: HDMI capture, in detail

For a live feed you convert the GoPro's clean HDMI into a normal USB video device:

HDMI out
Requires the GoPro Media Mod (micro-HDMI port). verified
Clean feed
GoPro Labs firmware + the MHDMI=1 setting gives an overlay-free feed that persists across reboots (with a * prefix). verified
Capture card
An HDMI→USB UVC grabber. A cheap MS2109 appears in Linux as an in-kernel uvcvideo /dev/video0 (MJPEG/YUYV, ~1080p). UMI names the Elgato HD60 X, which opens via cv2.CAP_V4L2. verified
As a device
It shows up as a standard /dev/videoX, so any v4l2/OpenCV consumer reads it like a webcam. verified
More detail · hardware caveats
The Elgato Cam Link 4K (used in some UMI docs) IS UVC but advertises formats it doesn't support, so OpenCV/ most V4L2 apps fail to open it directly and need a v4l2loopback+ffmpeg workaround — prefer the HD60 X or a plain MS2109. MS2109 grabbers can need a udev rule to unbind snd-usb-audio / bind uvcvideo, and image quality varies. A HERO13 firmware bug failed to go clean-on-boot if HDMI was connected before power-on; fixed in HERO13 v2.02.70 — workaround: plug HDMI after boot. UMI's exact chain: Media Mod 1.0 → Elgato HD60 X → UVC, opened with cv2.VideoCapture(path, cv2.CAP_V4L2), then a fisheye conversion + resize to 224×224; it auto-selects 3840×2160@30 ('Cam_Link_4K' in path) else 1920×1080@60.

11. What's required, and why each piece matters

🎥
For calibration only — nothing extra: record the board and calibrate offline. No capture card or Media Mod needed just to get intrinsics.
🧮
Double Sphere / EUCM model — needed for the clean wide fisheye (Max SuperView 167°). Without it the basic fisheye breaks (our "n/a"). OpenCV lacks it built-in; Kalibr / OpenImuCameraCalibrator have it.
🔌
Media Mod — gives the GoPro an HDMI output for a live feed. Without it: no HDMI → stuck on webcam → the mod can't work live.
🎛️
HDMI capture card (MS2109 / Elgato HD60 X) — turns HDMI into /dev/video. Without it the HDMI signal can't reach the computer.
💾
GoPro Labs firmware (MHDMI=1) — clean, persistent HDMI. Without it HDMI shows overlays and resets → unusable as a feed.
🎯
A larger ChArUco board — better corner precision and coverage. Helps; not the deciding factor.
Do we need a GoPro 9? No. UMI used a GoPro 9 + MLM 1.0, but that's just their choice — a GoPro 13 + Max Lens Mod 2.0 is fine. What's missing is not the camera; it's the connection method (HDMI + capture card, for a live feed) and the wide-angle model (Double Sphere). (Max Lens Mod 2.0 only fits HERO 12/13.)

"Narrowing to Linear" only suits cameras where wide FOV isn't required (it gives up the wide view, ~90–110°).

13. Caveats, confidence & corrections

Honest record of what is solid, what is inferred, and what we corrected during research:

  • "177°" is Max HyperView — anamorphic, not a clean fisheye. On the MLM 2.0 the calibratable clean fisheye is Max SuperView (167°); the marketed 177° "Max HyperView" is a non-uniform 8:7→16:9 stretch that no standard model fits. Earlier in this work we loosely called the lens "177°" — the usable clean mode is 167°. corrected
  • A GoPro 13 cannot hit a clean ~150–160°. The clean options are native Wide ~123° or MLM 2.0 Max SuperView 167°; the exact 155° belongs to the original Max Lens Mod 1.0, which GoPro does not list for the HERO 13 (HERO 9–12 only; "HERO13" in some shop listings is a retailer artifact, with poor-fit reports). verified
  • Matching UMI's exact 155° is not required. UMI is lens-agnostic given recalibration — drop new intrinsics into the UMI .json + ORB-SLAM3 .yaml. Any clean wide fisheye works with train/deploy consistency. verified (UMI issue #41)
  • Clean "Max" modes are recording/HDMI only. USB webcam mode can't select them, which is why the webcam capture produced the uncalibratable circular image. verified
  • The clean-vs-anamorphic split rests on a GoPro engineer's breakdown (Abe Kislevitz), verified directly, but GoPro's own product copy does not use the words "fisheye"/"anamorphic". Confirm the projection by reading the on-device lens menu + reported FOV before committing. inferred
  • UMI uses Kannala–Brandt, not Double Sphere. An early research pass claimed UMI calibrates with Double Sphere; the committed UMI artifact is intrinsic_type: FISHEYE (KB). OpenImuCameraCalibrator merely offers DS/EUCM. corrected
  • A "pinhole 30–40% worse / 0.150–0.235px" figure was unsupported. It was attributed to the Double Sphere paper's Table 1, which actually has no pinhole baseline. The paper only supports the weaker "pinhole suboptimal above 120°." Treat the specific number as fabricated. corrected
  • Gyroflow does not say SuperView "calibration fails unless reversed." It only says the modes are "not recommended" / "not exactly mapped." The strong calibration-failure claim is properly Joshi (ICRA 2022), not Gyroflow. corrected
  • HERO13 clean-HDMI-on-boot bug fixed in v2.02.70, not "v2.04.70" as first stated. corrected
  • No primary source demonstrates HERO12/13 clean-HDMI + Max Lens with zero vignette. That clean-image claim is mechanism-based inference, not a documented screenshot. inferred
  • "GoPro Labs required for persistent clean HDMI" is consistent with the UMI README but is an inference, not a verbatim source. inferred
  • Webcam fov= ignored (issue #459 WONTFIX) was not re-fetched in the last pass; plausible and consistent with our HERO11 observation, but verify empirically. inferred
  • KB model vs OpenCV implementation. "KB breaks beyond 180°" is true for OpenCV/Kalibr's pinhole-then- distort implementation; the KB model itself can fit ~190° with a proper implementation. nuance
  • cv2.omnidir result is our own measurement on one dataset (48px, unstable). It indicates OpenCV's omnidir is too fragile here, not that the omnidir model is wrong. A purpose-built DS/EUCM tool (Kalibr, OpenImuCameraCalibrator) is the reliable route. verified (on our data)
  • FastUMI's HDMI path is inferred from its use of an Elgato HD60 X; the text doesn't state webcam-vs-HDMI explicitly. inferred
  • Board coverage limit: on a circular fisheye the board never reaches the black-corner periphery, so the extreme edges of a wide (167°) lens are under-sampled — even a correct DS calibration will be best-constrained where the board actually went. verified
  • Run-folder names are unreliable (default gopro13_hyperview mislabels non-GoPro-13 runs). verified
